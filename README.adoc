= Mail System
:toc:
:toclevels: 3
:sectanchors:
:source-highlighter: rouge

Mail System is a full-stack web application for internal mail handling and shared support-mailbox integration.
It provides authenticated users with inbox, sent-mail, draft, compose, mail-detail and attachment workflows, while the backend integrates with a configured SMTP/IMAP mailbox for outgoing and incoming support messages.

The repository contains an Angular frontend, a Kotlin/Spring Boot backend and a Docker Compose runtime with PostgreSQL.

== System Overview

The system is designed as a split frontend/backend application:

* Angular single-page application served by Caddy in Docker.
* Kotlin/Spring Boot REST API for authentication, users, mails, recipients, attachments and mailbox integration.
* PostgreSQL database for Docker-based operation.
* H2 fallback database for direct local backend startup.
* SeaweedFS/S3-compatible object storage for uploaded and imported attachments.
* SMTP integration for sending mails through the configured support mailbox.
* IMAP polling for importing unread support-mailbox messages.

== Features

[cols="1,3",options="header"]
|===
| Area | Implemented behavior

| Authentication
| Users can register, log in, receive a JWT and access protected frontend routes and backend API endpoints.

| Mail folders
| Authenticated users can view incoming mails, sent mails and drafts.

| Mail composition
| Users can create drafts, edit drafts, send existing drafts and create-and-send mails in one flow. Each mail uses one explicit delivery mode: `INTERNAL` for registered application users or `EXTERNAL` for SMTP delivery through the configured THM mailbox.

| Recipients
| Internal mails use registered users as `TO`, `CC`, `BCC` and `REPLY_TO` recipients. External mails use manually entered email addresses for the same recipient categories. The backend rejects mixed internal/external recipient requests and prevents internal self-sending.

| Attachments
| Files can be uploaded, associated with mails, downloaded through the API and removed from storage when the mail is deleted.

| Shared support mailbox
| External incoming support mails sent to the configured THM address are imported once and are visible to all registered application users. External outgoing answers are sent through the same configured SMTP account. Internal messages remain inside the application and are not sent via SMTP.

| IMAP import
| Imported messages are stored as `RECEIVED`, keep external sender metadata, persist attachments, skip duplicate `Message-ID` values and are marked as read after successful handling. App-generated SMTP messages are marked with an origin header and ignored during IMAP import, which prevents duplicate inbox entries when SMTP and IMAP use the same THM mailbox.

| Ticket replies
| When a user replies to an imported support mail, the application presents a generated ticket number and prepends it to the outgoing reply subject if no ticket code already exists.

| Frontend integration
| The frontend renders internal senders and external IMAP senders consistently in inbox and mail-detail views, and provides a reply action for imported support mails.

| Local container runtime
| Docker Compose starts frontend, backend, PostgreSQL and SeaweedFS with persistent Docker volumes for database state and attachment objects.
|===

== Scope

The current project scope is mail management with shared support-mailbox import/export. Incoming support mails are treated as shared tickets for all registered users. Full ticket workflow management is outside the scope, but reply subjects include generated ticket numbers so support conversations can be tracked.

The Docker Compose setup is intended for local evaluation and development.
A public production deployment should provide production-grade secret management, TLS termination and operational monitoring.

== Architecture

At runtime, users access the Angular application through a browser.
Caddy serves the compiled frontend and reverse-proxies `/api/*` requests to the backend.
The backend owns business logic, persistence, security, attachment storage and SMTP/IMAP communication.

== Prerequisites

Install the following tools for local operation and development:

* Java 21
* Docker and Docker Compose
* Node.js and npm when working directly in `frontend/`
* A compatible SMTP/IMAP mailbox when testing real mail integration

The Gradle wrapper downloads the configured Gradle version automatically.
The Gradle-driven frontend build downloads the configured Node/npm versions through the Node Gradle plugin.

== Configuration

The Docker setup reads environment values from a root `.env` file.
Create it from the template and replace placeholder credentials before running the system:

[source,bash]
----
cp .env.example .env
----

Do not commit `.env` or any other file containing real credentials.
Only `.env.example` belongs in version control.

== Run With Docker

Build and start the complete stack:

[source,bash]
----
docker compose up --build
----

Open the application at:

* Frontend through Caddy: http://localhost:8081/app/
* Backend API through Caddy only: http://localhost:8081/api

Stop the system:

[source,bash]
----
docker compose down
----

Remove containers and persisted Docker volumes:

[source,bash]
----
docker compose down -v
----

== Run For Development

=== Backend

Start the backend from the repository root with the Gradle wrapper.
If mail credentials are stored in `.env`, export them before starting the process:

[source,bash]
----
set -a
source .env
set +a
./gradlew :backend:bootRun
----

The backend listens on http://localhost:8080.

=== Frontend

Start the Angular development server from the frontend module:

[source,bash]
----
cd frontend
npm install
npm run start
----

The frontend development server listens on http://localhost:4200.
It uses `frontend/proxy.conf.json` so browser requests to `/api/*` are forwarded to the backend on http://localhost:8080.
This mirrors the Docker setup, where Caddy performs the same `/api/*` reverse proxying.

If the backend URL changes, update `frontend/proxy.conf.json` and restart `npm run start`.

== Operational Notes

=== Authentication

The backend issues JWTs after successful login.
The frontend stores the token locally and adds it to API requests with an HTTP interceptor.

=== Attachments

Attachments are stored in SeaweedFS through its S3-compatible API.
The database stores attachment metadata and the object key used by the backend for download, delete and outgoing SMTP attachment loading.
In Docker, SeaweedFS persists objects in the `seaweedfs_data` volume.

=== Mail Sending

Internal mails are delivered inside the application only. They are visible to registered recipients through the local database and are not sent through SMTP.

External mails are sent through the configured SMTP account. The sender address is controlled by `SUPPORT_MAIL_ADDRESS`, which normally points to the same THM mailbox used for IMAP polling. Outgoing external messages include `X-Mail-System-Origin: mail-system` so the IMAP importer can identify and ignore copies generated by this application. Replies to imported support mails receive a `TICKET-000000` style ticket number in the subject when no ticket code exists yet.

=== Mail Receiving

IMAP polling is enabled in the backend application.
The scheduler uses `mail.polling.interval-ms` / `MAIL_POLLING_INTERVAL_MS` and imports unread messages through the same import flow used by diagnostics.
Imported messages are persisted as `RECEIVED`, duplicate `Message-ID` values are skipped, attachments are stored through the existing attachment storage, app-generated SMTP copies are skipped through the application origin header, and only successfully handled messages are marked as read on the IMAP server. Imported support mails are visible to all registered users.

Authenticated IMAP diagnostics are available under `/api/imap/diagnostics` for unread count, previews and manual import execution.

== Troubleshooting

=== Docker reports missing environment values

Check that `.env` exists in the repository root and contains all values listed in `.env.example`.

=== Backend image cannot find `/app/bin/backend`

Rebuild the Docker image from the repository root. The backend Dockerfile runs the Gradle Wrapper inside a multi-stage build; no manual local `installDist` step is required:

[source,bash]
----
docker compose up --build
----

=== Frontend cannot reach the API during development

For Docker, access the application through http://localhost:8081 so Caddy can proxy `/api/*` to the backend.
For separate development servers, make sure the backend is reachable on http://localhost:8080 and restart `npm run start` so Angular loads `proxy.conf.json`.

=== Database state should be reset

Remove Docker volumes:

[source,bash]
----
docker compose down -v
----
